When you press the power button on a modern machine, the CPU doesn't wake up as a 32-bit or 64-bit powerhouse. For backwards compatibility reasons, every x86 processor wakes up thinking it is a 16-bit processor from 1981. This is called Real Mode.
The motherboard's BIOS wakes up, does a quick hardware check (POST), and then looks for a storage device (a hard drive, a floppy disk, or a USB). But how does the BIOS know if a USB drive just holds MP3 files, or if it actually contains an Operating System?
It looks for the Master Boot Record (MBR).

The BIOS reads exactly the first 512 bytes (Sector 0) of your disk into memory.
To prove to the BIOS that this 512-byte block is actually a bootable operating system and not just random data, you must fulfill a strict mathematical contract:

    The Code: The first part of these 512 bytes must contain your executable machine code.

    The Padding: If your code doesn't take up the full 512 bytes (and it won't), you must fill the empty space with zeros.

    The Magic Number: The absolute last two bytes of the 512-byte block (bytes 511 and 512) must be the exact hex signature: 0x55 followed by 0xAA. (In assembly, we usually define this as a single "word" or 2-byte integer: 0xAA55 due to Little Endian architecture).

If the BIOS sees 0xAA55 at the end of the sector, it says, "This is an OS," hands full control of the CPU over to your code, and steps out of the way.


If we want to get back to writing a massive, high-performance kernel in pure C—with a multitasking scheduler, memory management, and a Virtual File System, we are going to need way more than 512 bytes.
The BIOS only loads the first 512 bytes (Sector 0) into RAM automatically. It doesn't care if you have a 10 GB hard drive attached; it stops reading after the magic 0xAA55 signature.
If we want to execute a larger C kernel, we have to teach our tiny 512-byte bootloader how to read a hard drive and manually pull the rest of the OS into RAM.
Just like the BIOS has a video driver (int 0x10) that we used to print a character, it also has a primitive disk driver: int 0x13.

In the 1980s, hard drives were physical spinning platters. To find data, the needle needed three coordinates: Cylinder, Head, and Sector (CHS).
    Sector 1: Contains our 512-byte boot.asm. (Notice that Sectors start counting at 1, not 0!)

    Sector 2: This is where our Stage 2 code will live on the disk.

our target coordinates to read from the disk are: Cylinder 0, Head 0, Sector 2.

We need a safe, empty place in physical RAM to dump the Stage 2 data.
Our boot.asm is currently sitting at 0x7C00. It takes up 512 bytes (up to 0x7DFF).
Let's dump our Stage 2 code safely above it at address 0x8000.

(Note: The BIOS uses a two-part pointer called es:bx to define this destination. To be safe, we must explicitly set the es (Extra Segment) register to 0 before we set bx to 0x8000.)

The BIOS checks the padding signature only for sector 1 after that, once we are in stage 2, we need to compile them and fuse them together so that boot.bin is exactly on sector1 and stage2.bin sits immediately after it on sector 2.
Once we are in Stage 2, the BIOS restrictions are gone. This file can be 5 bytes long or 50,000 bytes long.

    The BIOS wakes up and reads Sector 1 (boot.bin) into RAM at 0x7C00.

    Stage 1 takes over, commands the int 0x13 disk driver to read Sector 2 (stage2.bin) into RAM at 0x8000, and then blindly jumps there.

    Stage 2 wakes up at 0x8000, commands the int 0x10 video driver, and prints a 'K' to the screen before locking the CPU.

In the beginning the CPU is turned on, it thinks it's in the 1980s era and is trapped in real mode (16 bit mode), this is done to this date because of backward compatibility.
In 16 bit real mode, can only access a maximum of 1 Megabyte of RAM. There is zero security. Any program can overwrite the kernel or the BIOS and instantly fry the system. forced to use 16-bit assembly instructions. GCC and standard C compilers cannot generate 16-bit code natively.
with this the 16 bit real mode is over, and we can proceed to 32 bit protected mode.
To run a high-performance C kernel, we must upgrade the CPU to 32-Bit Protected Mode


-> Transitioning to 32 Bit Mode
Transitioning to 32-bit mode is a violent, one-way hardware maneuver. Once we flip the switch, the BIOS interrupts (int 0x10, int 0x13) will permanently cease to function. We will be entirely on our own.
the exact 4-step sequence we must write in stage2.asm to unlock the CPU:
    We must disable all hardware interrupts. If a keyboard press or a timer tick triggers an interrupt while we are halfway through upgrading the CPU architecture, the processor will panic and Triple Fault. This will be turned on after successfully transitioning.
    We must define a Global Descriptor Table. Because we are leaving the 1-Megabyte Real Mode limit, we have to tell the CPU exactly where the new 4-Gigabyte memory boundaries are, defining a secure 32-bit "Code Segment" and a 32-bit "Data Segment".
    We take the CR0 (Control Register 0) inside the CPU, and we physically flip its very first bit (the Protection Enable bit) from a 0 to a 1.
    The moment CR0 is flipped, the CPU is technically in 32-bit mode, but its internal pipelines are still clogged with leftover 16-bit instructions. We execute a massive "Far Jump" to a new memory segment to forcefully flush the CPU pipeline and land cleanly in the 32-bit world.

    In short, we need to turn on the A20 address line to transition to 32 bit mode... as A0 to A19 gives the memory usage upto 1MB.

-> GDT
In Real Mode, we saw how the CPU used es and bx to calculate memory (refer boot\es and bs segment mapping limitation.txt). In 32-bit Protected Mode, the CPU completely abandons that formula.

Instead, segment registers (cs, ds, es) no longer hold physical math. They become indexes that point to a massive array in memory called the GDT.
The GDT is a table of 8-byte structures (Descriptors) that define exactly where a block of memory starts, how big it is, and what security Ring is allowed to touch it.
To create a standard, high-performance "Flat Memory Model" (where the whole 4GB of RAM is accessible), we need exactly three entries in our GDT.

    The Null Descriptor
    The Intel manual dictates that the very first entry (Index 0) in the GDT must be exactly 8 bytes of zeros. This is a hardware safety net.
    If a rogue program accidentally uses a null pointer for a memory segment, it hits this empty descriptor and triggers a hardware exception instead of corrupting the system.

    The Code Segment Descriptor
    This entry (Index 1) will define the 4-Gigabyte arena where our C code will execute.
    Because Intel engineers had to cram this into 8 bytes while maintaining backwards compatibility with older chips, the layout of the bits is absolute madness.
    Instead of the Base and Limit being next to each other, they are fragmented.

    flag configuration we must map into those 8 bytes
        Base: 0x0 (Start at the absolute bottom of RAM)

        Limit: 0xFFFFF (The maximum size)

        Present: 1 (Yes, this memory exists in RAM)

        Privilege: 00 (Ring 0 - Maximum Kernel Authority)

        Executable: 1 (The CPU is allowed to run instructions here)

        Granularity: 1 (Multiply the limit by 4KB, stretching our 0xFFFFF limit out to a full 4 Gigabytes)

        Size: 1 (This is 32-bit protected mode code, not 16-bit)

    Data Segment Descriptor
    This entry (Index 2) defines the 4-Gigabyte arena for our variables, stacks, and data arrays. It is exactly identical to the Code Segment, with one tiny difference in the security flags:
        Executable: 0 (Do not execute data as code)
        Writable: 1 (We are allowed to change the variables)

-> 32-bit world
the moment flipped that CR0 switch and left Real Mode, we lost everything. The BIOS is gone. Standard interrupts are dead. If we try to call int 0x10 to print a character to the screen right now, the CPU will panic and crash.
before we can start building complex schedulers or memory managers, we need our kernel to be able to talk to us. We have to bypass the dead BIOS and talk directly to the physical video card on the motherboard.

-> Memory-Mapped I/O and the VGA Buffer
In standard programming, if we want to print something, we #include <stdio.h> and call printf().
Here on the bare metal, <stdio.h> does not exist. There is no standard library. There is no operating system underneath you to handle the text, you are the operating system.
To display text, we use Memory-Mapped I/O.

The hardware engineers hardwired the video card to constantly monitor a very specific chunk of our physical RAM. 
In standard VGA text mode, this chunk of memory starts at the exact physical address 0xB8000.
If you put a specific byte into address 0xB8000, the video card instantly snatches it and draws it on the top-left pixel of our monitor.

The video card doesn't just need to know what letter to print; it needs to know how to print it. Therefore, every single character on the screen requires exactly two bytes of memory:

    Byte 1 (The Character): The ASCII value of the letter want to print (e.g., 'X').
    Byte 2 (The Color): A special byte that defines the foreground text color and the background color.

The color byte is split into two 4-bit nibbles:

    The top 4 bits define the background color. (e.g., 0x0 is Black).
    The bottom 4 bits define the foreground color. (e.g., 0xF is White, 0x2 is Green).

    if we want to print a White 'X' on a Black background, the color byte would be 0x0F.

-> Compilation
Standard C compilers (like GCC) do not naturally build code for bare metal. By default, they try to compile executables for operating systems (like Linux or Windows), injecting massive standard libraries (libc), system hooks, and heavy memory overhead.
To ensure our C logic executes with absolute maximum speed and performance efficiency, we must instruct the compiler to generate raw, unadulterated 32-bit machine code.
To do this, we need an assembly bridge, specific compiler flags, and a raw linker command.

When the CPU jumps to our C code, it doesn't know what main() is. It blindly executes the very first physical byte of the file. If the C compiler decides to put a random helper variable at the top of the compiled file instead of our main() function, the CPU will execute that variable and crash.
We need a tiny assembly file whose only job is to be the physical first bytes of the kernel, acting as an anchor that safely calls our C function.

-> VGA Print Engine & VGA Text Algorithm
The VGA hardware doesn't understand pixels yet; it only understands character cells. It maps exactly 2,000 cells to our screen: 80 columns wide by 25 rows high.
RAM is one-dimensional (a flat line of bytes), but our screen is two-dimensional (X and Y coordinates). If we want to print a character at a specific row and column, we have to flatten those coordinates into a raw memory offset to add to 0xB8000.

algorithm: Offset = (Row * 80 + Column) * 2
We multiply the final result by 2 because of our 2-byte hardware contract: 1 byte for the Character, 1 byte for the Color

To print a continuous string, the kernel must keep track of its current position globally (using variables like cursor_row and cursor_col).
When we loop through a string character by character (checking for the \0 null terminator), the algorithm has to handle two strict edge cases:

    The Newline Intercept (\n): If the character is a newline, we can't push it to VGA memory (it will print a weird symbol). 
    our algorithm must intercept it, increment the cursor_row, and reset cursor_col to 0.

    The Screen Wrap: If cursor_col hits 80, the hardware won't automatically wrap for us. 
    our algorithm must manually catch it, reset cursor_col to 0, and increment cursor_row.


-> IDT 
Now that our kernel can speak and our memory map is under absolute control, we have to address the giant, gaping vulnerability currently sitting in our CPU.
Right now, our operating system is deaf, and it is walking on a tightrope without a safety net.

If we press a key on our keyboard, the keyboard hardware sends an electrical signal (an interrupt) to the CPU. Because we haven't told the CPU how to handle interrupts in 32-bit mode, it will panic, throw an exception, fail to find the exception handler, and Triple Fault (instantly crashing and rebooting the machine).
To stop the OS from crashing and to finally enable hardware input (like reading the keyboard), we must build the IDT.

The IDT is essentially an array of 256 pointers. When an interrupt fires (whether it's a keyboard press, a timer tick, or a "Divide by Zero" error), the CPU looks at this table to find the exact C function (Interrupt Service Routine, or ISR) it should run to handle the event.

The Interrupt Descriptor Table (IDT) is the cornerstone of interrupt and exception handling in x86 protected mode and long mode (IA‑32e). 
It replaces the real‑mode IVT (Interrupt Vector Table) and allows the operating system to attach a specific handler to each interrupt vector. 
Below is a full technical dissection, covering architecture, descriptor formats, the hardware algorithm, and programming details exactly as a computer engineer or low‑level programmer would need.

1. Role of the IDT
Mapping vectors to handlers – Each of the 256 possible interrupt/exception vectors (0–255) is associated with an IDT descriptor.

Gate mechanism – Instead of a simple jump target, the IDT uses gate descriptors that control privilege transitions, stack switching, and interrupt masking.

Protected transfers – When an interrupt occurs, the CPU consults the IDT to load a new CS:RIP (EIP) in a controlled way, automatically saving the old execution context.

Vectors 0–31 are reserved by Intel for exceptions. Vectors 32–255 are available for external (hardware) interrupts and software interrupts.


2. The IDTR Register
The location and size of the IDT are held in the IDTR (Interrupt Descriptor Table Register):

Mode	Format of IDTR	LIDT operand size
32‑bit	2 bytes LIMIT, 4 bytes BASE	6 bytes
64‑bit	2 bytes LIMIT, 8 bytes BASE	10 bytes
BASE – linear address of the start of the IDT.

LIMIT – size of the table in bytes minus 1. Because each entry is 8 bytes (32‑bit) or 16 bytes (64‑bit), the limit must be at least 8 * (max_vector + 1) - 1 or 16 * (max_vector + 1) - 1.
Loading the IDTR is done with LIDT m (privileged instruction, usually ring 0). Storing it is SIDT m.


3. IDT Descriptor Types
Three kinds of gate descriptors can reside in the IDT:

Interrupt gate (type 0xE) – used for hardware interrupts and most exceptions. Clears the IF (Interrupt Flag) upon entry, blocking maskable interrupts.

Trap gate (type 0xF) – used for exceptions that should not disable interrupts (e.g., debug exceptions). Does not clear IF.

Task gate (type 0x5) – used for hardware task switching (rare; not available in 64‑bit mode).

A descriptor marked Present=0 causes #NP (Segment Not Present) when referenced.


4. Interrupt / Exception Handling – The Hardware Algorithm
When an interrupt (hardware INTR, NMI, or exception) or a software interrupt (INT n, INT3, INTO) fires, the CPU executes the following micro‑architectural sequence. The description merges 32‑bit and 64‑bit specifics.

Step 1 – Determine Vector Number
For exceptions: fixed (e.g., #PF → 14).
For hardware interrupts: supplied by the interrupt controller (PIC/LAPIC) via the data bus.
For INT n: the immediate operand n.

Step 2 – Read IDT Descriptor
Compute offset in IDT: IDTR.base + vector * 8 (32‑bit) or * 16 (64‑bit).
If this address exceeds IDTR.base + IDTR.limit, signal #GP (General Protection).
Fetch the descriptor; check the Present bit. If 0 → #NP.
Validate Type:
    Interrupt gate (0xE) or trap gate (0xF) → continue.
    Task gate (0x5) → perform hardware task switch (only in 32‑bit mode; not described here).
    Else → #GP.

Step 3 – Privilege Checks
Hardware interrupts and exceptions (vectors 0–31, NMI, INTR) → gate DPL is ignored. They can transfer to a more privileged level, but the gate is always accessible regardless of CPL.
Software interrupts (INT n, INT3, INTO) → CPL must be ≤ gate DPL. If CPL > gate DPL, #GP. This prevents unprivileged code from using INT to call a ring‑0 handler unless the OS explicitly sets a gate’s DPL to 3.
Target code segment descriptor (referenced by the gate’s selector) must be:
A code segment (executable, non‑system).
Present → else #NP.
If the segment is conforming, the new CPL remains the old CPL; no stack switch.
If non‑conforming, the target DPL must be ≤ CPL (i.e., we can only transition to a higher or equal privilege level). If DPL > CPL → #GP.
If DPL < CPL, a stack switch will occur.

Step 4 – Determine Stack Switch and Load New Stack
A stack switch is required when target_DPL < CPL (i.e., we are entering a more privileged level).

32‑bit mode (no IST)
The processor reads the new SS:ESP pair from the TSS (Task State Segment) of the current task:

SS0:ESP0 for target ring 0
SS1:ESP1 for target ring 1
SS2:ESP2 for target ring 2

The SS selector is loaded, and its DPL must equal the target DPL, otherwise #TS (Invalid TSS). The new stack pointer is checked for alignment.

64‑bit mode
Two mechanisms exist:

    Legacy TSS – if IST = 0, the new RSP is taken from TSS.RSP0, RSP1, or RSP2 (depending on target privilege). SS is not loaded from the TSS; in 64‑bit mode SS is forced to a null selector with RPL = target DPL. The old SS and RSP are still pushed onto the new stack.

    Interrupt Stack Table (IST) – if IST ≠ 0, the processor ignores the privilege‑based stack pointers and loads RSP from TSS.IST[IST] (a pre‑initialised 64‑bit stack pointer). This is used for certain critical exceptions (e.g., #DF, NMI) to guarantee a known‑good stack. The IST mechanism always performs a “stack switch” even if CPL doesn’t change; the old SS:RSP is pushed.

In all cases, the new stack must be aligned to the appropriate boundary (16 bytes in 64‑bit mode, 4 bytes in 32‑bit mode after eventual pushes). A stack fault (#SS) is raised if the stack operations fail.

Step 5 – Save Old Context on the Stack
The processor pushes registers onto the new stack (or the current stack if no switch) in a fixed order.

32‑bit mode stack frame
If a stack switch occurred:

    Push old SS (32 bits, upper bits zeroed).

    Push old ESP.

    Then, in all cases:

    Push EFLAGS (32‑bit register).

    Push old CS (32 bits, upper bits zeroed).

    Push old EIP.

If the exception supplies an error code, push the 32‑bit error code.
Stack layout after interrupt with privilege change and error code (32‑bit):

... top of new stack (lowest address)
   error code        ← ESP after push
   old EIP
   old CS
   old EFLAGS
   old ESP
   old SS
... (higher addresses)

Without a privilege change, the SS & ESP are omitted.

64‑bit mode stack frame
If a stack switch occurs (whether via privilege change or IST):

    Push old SS (zero‑extended to 8 bytes).

    Push old RSP.

Then always:

    Push RFLAGS (8 bytes, upper 32 bits zeroed).

    Push old CS (zero‑extended to 8 bytes).

    Push old RIP.

If an error code is pushed, it is 8 bytes (zero‑extended).
The stack is always 16‑byte aligned before pushing the first item; pushes themselves naturally maintain alignment.

Step 6 – Load New Code Segment and Instruction Pointer
CS is loaded with the gate’s segment selector.

The new RIP/EIP is loaded with the gate’s offset.

If a stack switch happened, SS and RSP/ESP have already been set.

Step 7 – Clear Selected EFLAGS Bits
After loading CS:EIP but before the first instruction of the handler executes, the processor automatically modifies EFLAGS (RFLAGS):

TF (Trap Flag) ← 0 (prevents single‑step inside handler unless explicitly re‑enabled).
VM (Virtual‑8086 Mode) ← 0.
RF (Resume Flag) ← 0.
NT (Nested Task) ← 0.
For interrupt gates, additionally:

    IF (Interrupt Flag) ← 0 (maskable interrupts disabled).
    For trap gates, IF is not modified.

Step 8 – Begin Handler Execution
The CPU starts fetching instructions at the new CS:RIP in the target privilege level.

5. Error Code Details
Some exceptions push an error code to help the handler diagnose the cause. The error code format (same in 32‑bit and 64‑bit, zero‑extended when pushed) is:

 31            16 15     3 2 1 0
+----------------+--------+-+-+-+
| Reserved       | Index  |T|I|E|
+----------------+--------+-+-+-+
  E – External event (1 = hardware originated)
  I – Descriptor table (1 = IDT, 0 = GDT/LDT)
  T – Table indicator... with I: 1 = IDT, 0 = GDT/LDT (often combined)
 Index – Selector index involved

 Exceptions that do push an error code: #DF (8), #TS (10), #NP (11), #SS (12), #GP (13), #PF (14 – page fault; error code is page‑fault error format, different), #AC (17). All others (like #DE, #DB, #BP, #OF, #NM, etc.) push no error code.

6. Returning from an Interrupt – IRET / IRETD / IRETQ
The inverse operation restores the previously saved state.

Pop the items in reverse order, performing privilege checks:

    IRETD pops EIP, CS, EFLAGS; if return to a less privileged level, also pops ESP and SS.
    IRETQ pops RIP, CS, RFLAGS, and (if privilege change) RSP and SS.
    Privilege check for the return: the RPL of the popped CS and SS must be ≥ the current CPL. If returning to a lower privilege (CPL < CS.RPL), the new SS and ESP are validated.
    If the return is to VM86 mode (EFLAGS.VM=1), special stack handling occurs.
    Restores the processor state; the interrupted program continues at the popped CS:RIP (EIP).
    Software handling note: To remove the error code before IRET, the handler must manually pop it (e.g., add rsp, 8).

7. 64‑bit Mode Peculiarities
    Descriptor size – 16 bytes, with 64‑bit offset.
    IST – Enables per‑vector dedicated stacks, independent of privilege.
    No task gates – #GP if a task gate is referenced.
    Stack switching – SS is forced to a null selector, and the old SS is still pushed (IRETQ restores it). The TSS holds RSP0/1/2 and up to 7 IST pointers.
    Alignment – Stack must be 16‑byte aligned before the exception frame is pushed. The hardware automatically pushes items such that alignment is maintained.
    No automatic SS selector privilege check – Because SS is null, the CPU checks only that the new RSP from the TSS is canonical and the stack accesses are valid.

Fatal Problem 1: The Register Massacre
When you write normal C code, the compiler knows exactly when a function is being called. It follows standard calling conventions (like cdecl) and safely manages the CPU registers (EAX, EBX, ECX, etc.).

An interrupt, however, is entirely asynchronous.
Imagine your kernel is halfway through a complex math equation. It has crucial data stored in EAX and EBX. Suddenly, a hardware timer ticks, triggering an interrupt.

If the CPU jumps straight into your C page_fault_handler, that C code is going to start doing its own math. It will overwrite EAX and EBX to print text to the screen. When the C function finishes, it returns to your original math equation—but the registers have been silently overwritten. Your original program continues executing with corrupted data and completely collapses.

The Fix: We need an assembly stub to act as a "freeze-frame." The absolute first thing the stub must do is execute pushad (Push All Double-words). This saves all 8 general-purpose registers to the stack. We run the C code, and then execute popad to restore them. The interrupted program never even knows it was paused.



Fatal Problem 2: ret vs. iret
When a standard C function finishes, the compiler drops a ret (return) instruction at the end. The ret instruction assumes there is exactly one thing on the top of the stack: the memory address of where to go back to (EIP).

Hardware interrupts do not work this way.
Because interrupts happen violently and abruptly, the CPU automatically pushes three hidden things to the stack the moment the interrupt fires, not just one:

EFLAGS (The current status flags of the CPU)

CS (The Code Segment)

EIP (The instruction pointer to return to)

If your C function ends with a standard ret, the CPU will pull the EIP off the stack, but leave CS and EFLAGS sitting there, permanently misaligning your entire stack and instantly crashing the system.

The Fix: To return from an interrupt, you must use the iret (Interrupt Return) assembly instruction. iret specifically knows how to pop all three of those hidden values back into the CPU perfectly. A standard C compiler cannot generate an iret instruction.
