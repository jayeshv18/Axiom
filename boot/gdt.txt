Why do we need a GDT?
In 16-bit Real Mode, if we want to access memory, we use the hardware formula: (Segment * 16) + Offset.
If we put 0x1000 in a segment register, the CPU physically does the math and looks at memory address 0x10000.

In 32-bit Protected Mode, segment registers no longer contain physical addresses.
Instead, segment registers (cs, ds, es) contain Indexes (like an array index in C). When we tell the CPU to use segment 1, it looks up the 1st entry in a massive master list called the Global Descriptor Table (GDT).

The GDT is literally just a list of ID cards (Descriptors) for different chunks of memory. Each ID card tells the CPU:
Base: Exactly where this chunk of memory starts.
Limit: Exactly how big this chunk of memory is.
Access Byte: Who is allowed to touch it (Ring 0 Kernel vs Ring 3 User).
Flags: Is this code we can execute, or data we can write to?

To get our C kernel running, we don't want to chop our RAM into a million tiny, complex pieces. We want one massive, unsegmented 4-Gigabyte playground. This is called the Flat Memory Model.
To build this, our GDT array needs exactly three ID cards:

    Index 0: The Null Descriptor. (Mandatory safety feature. It must be exactly 8 bytes of zeros. If a program uses a null pointer, it hits this and crashes safely).
    Index 1: The Code Segment. (Starts at 0x0, stretches across all 4GB, marked as Ring-0 Executable).
    Index 2: The Data Segment. (Starts at 0x0, stretches across all 4GB, marked as Ring-0 Writable).

Here is where the algorithm gets messy. Back in the 1980s, Intel had to maintain backwards compatibility with older chips. So, instead of making the 8-byte descriptor nice and clean (e.g., 4 bytes for Base, 4 bytes for Limit), they chopped the bits up and scattered them.
To create one 8-byte descriptor, we have to map out the bits exactly like this:
    Bytes 0-1: Limit Low (The first 16 bits of the size)
    Bytes 2-3: Base Low (The first 16 bits of the starting address)
    Byte 4: Base Middle (The next 8 bits of the starting address)
    Byte 5: Access Byte (Security flags - Ring 0, Present, Executable, etc.)
    Byte 6: Flags + Limit High (4 bits for granularity/32-bit mode + the last 4 bits of the size)
    Byte 7: Base High (The last 8 bits of the starting address)

We want a Base of 0x00000000 and a Limit of 0xFFFFF (with a flag that multiplies the limit by 4KB to reach 4GB).
    Limit Low: 0xFFFF
    Base Low: 0x0000
    Base Middle: 0x00
    Access Byte (Code): 10011010 in binary (which is 0x9A in hex)
    Flags + Limit High: 11001111 in binary (which is 0xCF in hex)
    Base High: 0x00

-> Simplified Explanation

We want this Code Segment to start at the absolute bottom of physical RAM (address 0) and stretch all the way to the 4-Gigabyte ceiling.
This is the easiest part. We want the memory to start at 0x00000000 (a 32-bit zero).
Because of Intel's fragmented 8-byte blueprint, we have to chop that 32-bit zero into three pieces:
    Base Low (16 bits): 0x0000
    Base Middle (8 bits): 0x00
    Base High (8 bits): 0x00
    If you stitch them back together, they equal exactly 0x00000000.

Here is where the math gets fascinating. We want a size of 4 Gigabytes. In hexadecimal, 4GB is 0xFFFFFFFF (32 bits long).
Intel only gave us 20 bits to define the Limit inside the descriptor. The maximum number a 20-bit register can hold is 0xFFFFF.
If you convert 0xFFFFF to decimal, it is exactly 1,048,575 bytes (1 Megabyte). If we just use that, our kernel will crash the second it tries to use more than 1MB of RAM.

Solution: The Granularity Multiplier
Intel added a special flag called the Granularity Bit.
If you set this bit to 1, the CPU takes your 20-bit limit and physically multiplies it by 4 Kilobytes (0x1000 in hex).
0xFFFFF (Our 20-bit Limit) * 0x1000 (The 4KB Multiplier) = 0xFFFFFFFF (4 Gigabytes!)

So, our raw Limit value needs to be 0xFFFFF. We chop this into two pieces:
Limit Low (16 bits): 0xFFFF
Limit High (4 bits): 1111 in binary (which is hex 0xF. We will fuse this with the Flags byte).

This single byte defines the laws for this segment. Let's read the binary from left to right (Bit 7 down to Bit 0):
    Bit 7 (Present) = 1: "Yes, this segment physically exists in RAM."
    Bits 6 & 5 (Privilege) = 00: "This is Ring 0." (If we were making a user-space application segment later, this would be 11 for Ring 3).
    Bit 4 (Descriptor Type) = 1: "This is a memory segment, not a system trap gate."
    Bit 3 (Executable) = 1: "The CPU is allowed to run code here." (For the Data Segment, this is 0).
    Bit 2 (Conforming) = 0: "Lower privilege rings cannot jump into this code."
    Bit 1 (Readable) = 1: "We can read the raw bytes of the code."
    Bit 0 (Accessed) = 0: "The CPU will flip this to 1 when it uses it. We start it at 0."
    Result: 10011010b (Hex: 0x9A)
